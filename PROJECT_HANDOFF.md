## Для чего проект

Отчёт о рабочих задачах отдела по разрешённым Telegram-перепискам и Asana-уведомлениям.
Нужны входящие и завершённые задачи, известный открытый остаток, время решения,
реестр и проверяемые исходные сообщения. AIO/TheRaw — только происхождение оформления,
их API и рабочие БД в этот проект не входят.

Единица учёта — задача, не сообщение и не Destination. Несколько дестов одного
запроса не создают автоматически несколько задач. Совпадение Telegram и Asana
подтверждается ID/доказательствами, а не только похожими названиями.

## Целевой рабочий процесс

1. VPS собирает сообщения и правки один раз в сутки, в **00:10 Europe/Moscow**,
   через два разрешённых рабочих Telegram-аккаунта. Это цель; старый cron пока 15-минутный.
2. Подготовщик сохраняет исходные версии и неизменяемые дневные пакеты с manifest,
   контрольными суммами, охватом, reply/topic и точными Asana-ссылками. Для модели
   формируется отдельная копия без секретов, сохраняющая ссылки на оригинальные ревизии.
3. Пользователь в локальном Codex пишет «Обработай новые данные». Codex самостоятельно
   читает пакеты и текущие задачи через SSH. Постоянных ручных ZIP/переименований не должно быть.
4. Codex создаёт предложения с событиями и evidence по существующей JSON-схеме.
   Код проверяет их и импортирует в PostgreSQL; принятие — отдельное действие
   в рамках разрешения пользователя. Неоднозначное остаётся на проверке.
5. Codex проверяет импорт и API дашборда. Пакет отмечается обработанным только после
   успешного завершения; повтор не создаёт дубли. Интерфейс читает готовую модель.

Сбор автоматический, смысловой анализ запускается вручную. Ночные обращения к модели
через API не согласованы. Полная цепочка выше ещё **не реализована end-to-end**.

## Правила показателей

- «Поступило»: уникальные принятые задачи с первым допустимым `requested` в периоде.
  Назначение `assigned` и время импорта не заменяют время запроса.
- «Завершено»: уникальные принятые задачи с доказанным допустимым `completed` в периоде.
  Повторное завершение после `reopened` отдельно учитывается как событие.
- «Известно открытых»: остаток известных открытых задач на конец периода, включая
  более раннюю историю. Дневные остатки не суммируются; полнота отдела не предполагается.
- Время решения: медиана календарного интервала от известного запроса до завершения,
  включая ожидание. Не трудозатраты; неизвестное начало даёт неизвестный интервал.
- Отчётные дни — Москва, недели с понедельника; даты выбранного периода включительны.
- Общий аккаунт, смена, автор комментария и исполнитель — не одно и то же.
  Неизвестного исполнителя не угадывать. Pending proposals в показатели не входят.

Точные правила и пограничные случаи: [BACKEND_SEMANTICS](docs/BACKEND_SEMANTICS.md).

## Контракт, который действительно принимает код

Данные PostgreSQL: `raw.*` — сообщения/ревизии; `work.*` — предложения/задачи/события/evidence;
`ops.*` — импорты и журнал решений. DDL: [init/10-schema.sql](init/10-schema.sql).
UI/API читают отчётные данные; admin может записывать только отдельные UI-настройки раскладки.
Запись задач и review выполняет `sync.py` с отдельной ролью writer.

Выход Codex: `{ "schema_version": 1, "proposals": [...] }` по
[task-proposals.schema.json](examples/task-proposals.schema.json).
Нужны `proposal_id`, `task_id`, `version`, поля задачи, события и точные пары
`message_key`/`revision_hash`. Сохранять ID и историю уже известных задач.
Формат `{ "tasks": [...] }` с `task_key` из старого черновика не является входом текущего importer.

Жизненный цикл задают события `requested`, `observed_open`, `assigned`, `waiting`,
`resumed`, `work_ready`, `completed`, `reopened`, `cancelled`, а не свободно записанное поле `state`.
`work_ready` — ещё открытая задача. Решение review хранится отдельно как
`proposed`/`accepted`/`rejected`; `review_required=false` не считается принятием.

Использовать [EXTRACTION_PROMPT](docs/EXTRACTION_PROMPT.md). Проверка proposals
с `--dry-run --messages` проверяет evidence по bundle; без `--messages` это только
`syntax_only`. Для изменения принятой задачи нужны полный snapshot и ожидаемая revision.

## Что есть и что осталось

Есть действующий старый dashboard, PostgreSQL, importer/review, локальная копия
кода и отдельный Linux collector на Telethon/SQLite. Старый сервер проверялся ранее
23 октября; контрольные значения и локальные тесты записаны в [STATUS](docs/STATUS.md).

Остаются: два рабочих аккаунта, дневные пакеты и журнал обработки, сохранение
entities/href/topic, безопасная очистка для модели, согласование message IDs между
collector и importer, общий повторяемый ручной запуск Codex и проверка всей цепочки.
Упомянутый облачным чатом `team-activity-ingest.zip` описывает другой вариант collector;
его исходники не приложены к handoff и не подменяют проверенный код в `collector/`.

Переносить нужно не только контейнер: отдельно код, PostgreSQL dump, collector state,
входные пакеты и защищённую конфигурацию/сессии. План и приёмка: [MIGRATION](docs/MIGRATION.md).
Старые сервисы/данные не удалять до проверенного восстановления. Secrets, sessions,
переписка и дампы не публикуются в Git.
