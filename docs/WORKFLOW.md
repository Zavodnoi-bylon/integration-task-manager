# Рабочий процесс проекта

Актуально на 23 октября 2026. Это краткий контракт для человека и Codex, без истории споров и промежуточных идей.
Общий вход в проект — [PROJECT_HANDOFF.md](../PROJECT_HANDOFF.md); расхождения с прежними черновиками разобраны в STATUS.md.

## Назначение

Team Activity Explorer показывает работу отдела интеграций по задачам и подтверждённым результатам. Источники — выбранные Telegram-переписки, темы передачи смены и уведомления Asana. Единица учёта — задача, а не сообщение. AIO/TheRaw — происхождение части интерфейса, но не источники данных этого проекта.

## Согласованный поток

1. Новый VPS один раз в сутки, в **00:10 Europe/Moscow**, собирает новые сообщения и изменения через два рабочих Telegram-аккаунта. Первый источник включает уведомления Asana и выбранные чаты, второй — выбранный чат. Точные разрешённые чаты задаются конфигурацией. Тестовая сессия не считается рабочей.
2. Подготовщик сохраняет неизменяемый пакет за период с ID сообщений, автором, временем, правками, темой и связями ответов. Нужны manifest, контрольные суммы и охват источников. Пропущенные дни должны догружаться по checkpoint, а не теряться.
   Секреты исключаются из отдельной копии для модели; защищённые оригиналы не переписываются. Копия сохраняет ссылки на исходные `message_key`/`revision_hash`. Политика очистки не должна уничтожать технические ID, нужные для сопоставления. Автоматическая безопасная подготовка этой копии ещё требует реализации и тестов.
3. Пользователь открывает локальный проект в Codex на Windows и пишет: «Обработай новые данные». Компьютер должен быть включён для этого этапа.
4. Codex через SSH забирает ещё не обработанные пакеты и текущий реестр задач/версий. По `EXTRACTION_PROMPT.md` готовит JSON предложений с доказательствами по `examples/task-proposals.schema.json`.
5. Код проверяет формат, жизненный цикл, точные ссылки на сообщения и повторную загрузку. Затем адаптер импортирует сообщения и предложения в PostgreSQL. Подтверждение задач выполняется в рамках явно данного пользователем разрешения; неоднозначные случаи остаются в очереди.
6. Codex сверяет результат в API дашборда. Пакет отмечается обработанным только после успешной транзакции и проверки. Повторный запуск не должен создавать дубли.
7. Пользователь смотрит отчёт и очередь проверки в дашборде.

Ночной вызов модели через API не входит в этот процесс. Автопарсер не выполняет смысловой анализ и не принимает задачи самостоятельно. Excel — дополнительный экспорт, он не заменяет базу.

## Правила отчёта

- Назначение Asana = `assigned`; новый запрос = `requested`. Эти события не взаимозаменяемы.
- `completed` требует подтверждения; «сделай» и «почти готово» не равны завершению.
- Общее имя Telegram-аккаунта не определяет сотрудника. Неизвестный исполнитель остаётся `null`.
- Совпадения между перепиской и Asana проверяются по ID и доказательствам; похожие названия не дают права объединять задачи.
- Несколько Destination одного запроса не означают несколько задач; их ID сохраняются строками в `external_refs`.
- Сохраняются исходные ревизии сообщений; новые правки не переписывают основания прежнего решения.
- Отсутствие сообщения в частичном экспорте не означает удаление или завершение задачи.
- «Известно открытых» не равно полному backlog отдела. Интервалы между сообщениями не равны трудозатратам.

## Контракт данных

Исходные сообщения и ревизии: `raw.*`. Предложения/задачи/события/evidence: `work.*`. Импорты/журнал решений/охват: `ops.*`.
Точная схема: `init/10-schema.sql`; семантика: `ARCHITECTURE.md`, `BACKEND_SEMANTICS.md`.
UI имеет только чтение. Запись — через `sync.py`, роль `activity_writer`; администрирование БД — отдельно.
Формат предложений — `schema_version:1` с массивом `proposals`, не `tasks`. Вариант `activity_ingest.task_candidates`/`task_key` из переданного облачным чатом handoff относится к другому прототипу и не является контрактом текущего UI/importer.

## Что ещё не реализовано

Два независимых аккаунта, сохранение тем, дневные пакеты/manifest, полный мост collector → dashboard и журнал завершённых аналитических пакетов. Текущий collector JSON и формат `sync.py normalize` различаются. Нельзя просто подать `collector/data/normalized/messages.json` в существующий importer и назвать цепочку готовой.

При реализации моста нужно сохранить entities/href Asana, raw timestamps и reply/topic. Сейчас collector сохраняет упрощённый текст и метаданные; восстановить утраченные ссылки из уже упрощённого JSON нельзя. Namespace `telegram:` у collector и `telegram-desktop:` у importer также требует явного сопоставления без дублей.
