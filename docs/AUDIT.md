# Аудит AIO Explorer и TheRaw Explorer

**Дата:** 22 октября 2026 года.  
**Цель:** выбрать основу отчётности отдела по задачам из Telegram и Asana,
добавить динамику по дням/неделям, подготовить отдельный проект локально.

## 1. Вывод

**TheRaw Explorer подходит как основа нового приложения. В готовом виде оба
исходных интерфейса показывают KPI и таблицы; графиков в них нет.** Отсутствие
графиков не является ограничением выбранного стека: их можно добавить без
замены FastAPI, JavaScript и PostgreSQL. В новом локальном проекте такие графики
уже реализованы, вместе с реестром и доказательствами из сообщений.

TheRaw предпочтительнее благодаря собственной БД, отдельным ролям и понятному
разделению reader/UI и writer/import. Но это не универсальная BI-платформа,
в которую достаточно подать произвольный JSON. Модель визитов/конверсий,
загрузчик, SQL и арифметику метрик необходимо заменить. Буквальная копия старого
installer для нового проекта небезопасна из-за привязок к действующим сервисам.

Для вашей задачи основная сложность — достоверно выделить задачи и связать
запрос с завершением. Отрисовка графика значительно проще. Поэтому новая модель
разделяет исходные сообщения, предложения ИИ и подтверждённые карточки.

описанию сервера, а не к новой проверке его состояния.

## 4. Как устроены исходные приложения

### AIO Explorer

Vite собирает frontend, FastAPI обслуживает его и GET API из одного контейнера.
`/api/meta` возвращает фильтры и список метрик, `/api/destinations` — справочник,
`/api/cube` — сгруппированные значения, `/api/events` — детализацию.
Данные приходят из `core.conversions`, `analytics.bi_filter_values` и
`finance.fx_rates`. Суммы конверсий и денежные показатели вычисляются SQL,
затем frontend выполняет дополнительную группировку под выбранные колонки.

Полезная деталь: фильтр дат использует границы timestamp, а cube получает
детальные строки и grand total через один `GROUPING SETS` запрос
(`app.py:105–106, 254–301`). Денежная логика и курсы валют для нового отчёта не нужны.

### TheRaw Explorer

Compose содержит PostgreSQL, reader-приложение и отдельно запускаемый sync.
Схема содержит `core.visits`, `core.conversions`, `ops.sync_runs`.
`sync.py` забирает данные upstream API, нормализует и UPSERT-ит их;
backfill-скрипты дополняют историю и идентификаторы.
Таймер запускает повторную синхронизацию с перекрывающимся интервалом.

UI/API показывает Visits, Registration, FTD и производные отношения,
группирует таблицу и раскрывает последние события. Экспорт отдаёт идентификаторы
визитов для двух специальных сценариев. Перед началом HTTP-выдачи экспорт
полностью подготавливается и ограничивается по строкам/байтам — полезный
паттерн для новой выгрузки (`app.py:294–357`).

**Расхождение с прежней справкой:** оба исходных `app.py` явно задают
`docs_url=None, redoc_url=None` (AIO:16, TheRaw:35). Swagger `/docs` отключён.
Из-за SPA fallback запрос `/docs` может возвращать HTML основного интерфейса;
одного HTTP 200 недостаточно, чтобы считать Swagger доступным.
OpenAPI по умолчанию отдельно не отключён.

## 5. Находки, требующие внимания

### 5.1. Web-контейнер TheRaw получает лишние credentials

`theraw-analytics/compose.yaml:33` передаёт explorer весь `env_file: .env`.
Установщик формирует в этом файле admin/writer/reader-переменные
(`install.sh:25–29`). Переопределение `DB_USER=theraw_reader` не удаляет из
окружения другие пароли. Роль подключения read-only полезна, но изоляция
credentials процесса остаётся слабее заявленной.

**В новом проекте:** web получает только явные DB_* reader-параметры.
Writer доступен только CLI, admin — только Postgres/init. Содержимое настоящего
`.env` для этого вывода не требуется и не читалось.

### 5.2. Cube может молча обрезаться

AIO ограничивает общий результат `LIMIT 20001`, включая total
(`app.py:297, 313–317`); TheRaw — `LIMIT 20000` на строки и отдельный запрос
итогов (`app.py:227, 229–254`). Явного признака неполноты cube нет.
Если групп окажется больше лимита, таблица и последующая frontend-группировка
покажут часть данных, а KPI могут содержать полный итог.

Это подтверждённый путь выполнения, но наличие 20 тыс. групп в реальной БД
не измерялось. **В новой версии:** агрегаты строятся по целому ограниченному
снимку; превышение лимита даёт явную ошибку. Реестр имеет серверную пагинацию.

### 5.3. Старую арифметику нельзя переносить на задачи

`groupRows()` в обоих проектах суммирует значения всех метрик
(AIO `src/main.js:295–310`, TheRaw `301–316`). Такая арифметика пригодна для
аддитивных счётчиков, но неверна для остатка открытых задач, медиан и некоторых
distinct counts. Например, сумма семи дневных остатков не означает недельную
нагрузку. Это ограничение повторного использования, а не утверждение, что
все существующие AIO-счётчики неверны.

**В новом проекте:** дневные/недельные ряды и period totals вычисляет сервер
по истории событий с отдельными правилами для потоков и остатков.

### 5.4. Гонка ответов в AIO

AIO присваивает глобальный `latestPayload = await response.json()` до проверки
актуальности requestId (`src/main.js:495–496`). Более старый JSON может заменить
глобальные totals после того, как новая таблица уже загружена. Этот сценарий
воспроизведён локально с управляемым порядком ответов.

TheRaw сначала читает ответ в локальную переменную, проверяет ID и только затем
публикует состояние (`569–573`); в том же сценарии результат согласован.
Новый frontend использует gate актуальности и AbortController.

### 5.5. Ошибка загрузки может оставить старые цифры рядом с новыми фильтрами

TheRaw при неудачном обновлении сохраняет прежние строки/KPI и меняет статус
(`src/main.js:550–585`). Детализация строит параметры из текущей формы
(TheRaw `407–423`, AIO `401–415`). Поэтому старые строки могут раскрывать уже
другой срез, если фильтры изменены, а новый запрос не завершился успешно.

**В новой версии:** детализация/CSV используют параметры загруженного отчёта;
ошибка нового отчёта очищает прежние цифры и отключает действия.

### 5.6. «Сегодня» зависит от часового пояса браузера

Быстрые периоды используют локальный `new Date()` и `getFullYear/getMonth/getDate`
(AIO `src/main.js:183–204`, TheRaw `189–210`), хотя SQL считает дни по Москве.
При другом часовом поясе пользователя возможен сдвиг выбранного дня.
Форматирование времени последнего события, напротив, явно использует Москву.

**В новой версии:** сервер отдаёт московскую дату; пресеты строятся от неё.

### 5.7. В TheRaw детализация не сохраняет валюту строки

Cube группируется по currency (`app.py:220, 226`), но event_filters и frontend
drilldown её не передают (`app.py:115–131`, `src/main.js:409–417`). Для строки
конкретной валюты детализация может захватить другую валюту при прочих равных.
Кроме того, общий SUM revenue без нормализации валют не является сопоставимой
денежной суммой, если в выборке присутствует несколько валют.

Наличие фактически смешанных валют не проверялось. В новой предметной модели
эти финансовые метрики полностью отсутствуют.

### 5.8. Потенциальная потеря использования timestamp-индексов

TheRaw фильтрует по `(event_at AT TIME ZONE 'Europe/Moscow')::date`
(`app.py:19, 90`), а схема создаёт обычные индексы timestamp
(`init/10-schema.sql:62, 67`). Условие по вычисляемому выражению может не
использовать эти индексы как прямой диапазон. Без EXPLAIN на реальной БД нельзя
утверждать, что запрос сейчас медленный. Для нового SQL лучше использовать
полуоткрытые UTC-границы, как уже делает AIO.

### 5.9. Строки и totals TheRaw могут читать разные состояния БД

Два SELECT выполняются последовательно (`app.py:240–244`) без REPEATABLE READ.
При параллельном sync транзакция READ COMMITTED допускает разные снимки
для двух операторов. Это возможная гонка, не доказанное расхождение production.
В новой версии каждый ответ строится внутри одной read-only REPEATABLE READ
транзакции. Это не фиксирует состояние между разными HTTP-запросами.

### 5.10. Установщик привязан к существующим сервисам

`install.sh` содержит пути текущих проектов/Vaultwarden/Caddy (4–8), копирует
AIO API token (34), правит и перезагружает Caddy (63–80), устанавливает systemd
и запускает import (83–87). Также он сохраняет и выводит файл с UI-паролем (41,91).
`fix-sync.sh:4–8` останавливает целевые sync-контейнеры и повторно запускает installer.

**Вывод:** эти скрипты не выполнялись и не перенесены в новый проект.
Подготовлены самостоятельные команды для нового каталога; root-действия
вынесены в отдельную инструкцию пользователя.

### 5.11. Документация расходится с текущим окном синхронизации

README TheRaw говорит о семи днях (`README.md:11`), тогда как Compose, unit и
default sync используют два (`compose.yaml:71`, `systemd/theraw-sync.service:10`,
`sync.py:384`). Исправление старой записи за пределами окна может не обновиться
обычным повторным проходом. Для Telegram нужна версионная модель сообщений,
а не предположение, что успешно пройденный временной интервал навсегда закрыт.

### 5.12. UPSERT не защищает от устаревшего источника

TheRaw обновляет данные по ключу без сравнения свежести источника
(`sync.py:202–218, 227–242`). Старый повторный payload способен заменить новое
значение. `COALESCE` при обновлении части полей мешает явному очищению ошибочного
значения. Такой подход нельзя копировать для ручных решений об исполнителе.

**В новом проекте:** неизменяемые ревизии, сравнение времени обновления,
отдельная отметка конфликта, полные review-снимки и защита revision.

### 5.13. Нет общей блокировки импортов

Hourly, initial и backfill могут пересекаться. `sync.py:330–334` использует
один временный state-файл; installer запускает initial без гарантированной
остановки уже работающего таймера. Это риск гонки при одновременном запуске,
а не установленный факт потери данных. Новый importer использует общий
PostgreSQL advisory lock и транзакции.

### 5.14. Неполный сегодняшний день backfill может стать «обработанным»

Identity backfill ограничивает последний интервал текущим временем, но сохраняет
checkpoint по дню (`identity_backfill.py:33,40–48,87–88`); следующий проход
может пропустить оставшуюся часть такого дня. Аналогичный паттерн есть в
обработке visits (100–108,147–148). Для нового сборщика требуется cursor/watermark
с перекрытием и дедупликацией по сообщениям, а не окончательная отметка суток.

### 5.15. Init SQL не заменяет миграции

Схема содержит buyer-поля (`init/10-schema.sql:50–52`), но Docker init применяется
только при создании volume (`compose.yaml:18`). Установщик отдельно мигрирует
лишь часть currency/revenue-полей (`install.sh:56–57`). Старый volume может
отличаться от текущего init; актуальная схема production не проверялась.
Новый init рассчитан на новый volume; дальнейшие версии потребуют миграций.

### 5.16. Журнал и резервные копии неполны в рамках переданного кода

`ops.sync_runs` хранит финальную успешную сводку; полноценного append-only журнала
ошибок и решений оператора в этой модели нет. В переданных файлах есть backup
Caddyfile, но нет процедуры backup/restore PostgreSQL. Это не означает, что
резервные копии не организованы где-то ещё на VPS.

В новом проекте предусмотрены import status/error_code, review_log,
отдельный pg_dump script и пробное восстановление в другую БД. Расписание
и внешнее хранение резервных копий пока не настроены.

### 5.17. Зависимости и воспроизводимость

Оба Dockerfile делают `npm install` только по package.json; lock отсутствует.
Прямые Python-зависимости закреплены, транзитивные — нет. Образы используют
изменяемые теги. Повторная сборка может получить другой набор библиотек.

Для исходного Vite 7.1.4 `npm audit` показал известные advisories, в том числе
для доступного по сети dev server. Maintainer указывает исправления в ветке 7,
включая 7.3.7 для октябрьского advisory [E1, E2]. В исходных production Dockerfile
Vite используется на стадии сборки, поэтому этот вывод нельзя автоматически
переносить на открытый production API как утверждение об эксплуатации.

Локальная установка старого Python-набора разрешила Starlette 0.46.2.
Проверка обнаружила advisories, в частности Range-header DoS в FileResponse;
исходные приложения используют FileResponse [E3]. Реальный установленный
на VPS пакет и доступность атаки через proxy не тестировались.

**Новый проект:** Vite 7.3.7, FastAPI 0.159.1, Starlette 1.9.0;
все прямые и транзитивные версии записаны в lock-файлы. Итог сканирования
зафиксирован в `VERIFICATION.md`. Нулевой результат advisory scan означает
только отсутствие известных совпадений в использованной базе на дату проверки.

### 5.18. Дополнительные ограничения UI

В детализации показываются последние 500 событий с предупреждением, но перехода
на следующую страницу нет. Основная таблица не имеет серверной пагинации.
Автоматического обновления нет. Часть преобразований `Number(value) || 0`
смешивает неизвестное значение и ноль. Повторное открытие редактора колонок
добавляет dragover listener; записи localStorage не везде обёрнуты в обработку
ошибок. Фильтр может исключить выбранное значение, пропавшее из справочника,
без явного объяснения пользователю.

Это причины выбирать отдельную простую страницу графиков и реестр, а не
переносить весь старый универсальный конструктор таблиц. Найденные точки
HTML-вставки экранируют пользовательские строки, SQL-фильтры параметризованы;
явных SQL injection/DOM XSS в изученных путях не обнаружено. Это не отдельный
пентест и не гарантия безопасности всего окружения.

## 6. Что переиспользовать без изменений

Следует различать «подходит для копирования» и «фактически скопировано».

| Компонент | Можно оставить буквально | Что сделано в новом проекте |
|---|---|---|
| CSS-тема TheRaw | Да, как базовый слой | `src/base.css` побайтово совпадает с оригиналом; новые стили отдельно |
| `escapeHtml` | Да | Тело функции сохранено; новое содержимое также экранируется |
| Форматирование MSK timestamp | Да, при прежнем контракте | Сохранён принцип явного timezone, новые русские подписи |
| Resize-утилиты колонок | Да, при прежней разметке и новых storage keys | Не включены: первая версия делает акцент на графиках и простом реестре |
| Шаблоны KPI/table rendering | Условно: если сохранить формат metadata | Общая идея сохранена, значения/семантика переписаны |
| Vite config исходников | Файлы у двух проектов совпадают | В новой версии добавлен API dev proxy и разрешённый preview-host |
| Multi-stage Docker + непривилегированный web user | Архитектурный шаблон | Пересобрано с lock-файлами и новыми COPY/ENV |
| Read-only API и отдельный writer | Архитектурный шаблон | Усилено разграничение credentials и SQL grants |
| SQL AIO/Visits, таблицы конверсий | Нет | Новые таблицы задач/событий/доказательств |
| `sync.py` и backfill | Нет | Новый импорт сообщений и review CLI |
| `groupRows`, проценты, денежные метрики | Нет | Серверные правила flow/stock/distinct/median |
| Installer, paths, credentials, proxy aliases | Нет | Отдельные ресурсы и команды пользователя |

Нельзя обещать, что «90% приложения уже готово»: визуальная оболочка переиспользуется
хорошо, а основная логика новой предметной области создаётся заново.

## 7. Подготовленный новый проект

`team-activity-explorer/` содержит схему, роли, importer, review, GET API,
SVG-графики, фильтры, реестр, CSV, карточки и тесты. Полная архитектура —
`ARCHITECTURE.md`, правила backend — `BACKEND_SEMANTICS.md`, результаты —
`VERIFICATION.md`, команды запуска — `DEPLOYMENT.md`.

Внутреннее хранилище имеет три уровня:

1. **Что было написано:** оригинальные сообщения и версии.
2. **Как это интерпретировано:** предложения ИИ с доказательствами.
3. **Что принято в отчёт:** проверенные задачи и события.

Это позволяет повторить обработку другой моделью, исправить ошибку и объяснить
руководству происхождение любой цифры. AI confidence не используется как
математическое доказательство правильности или автоматическое разрешение записи.

## 8. Рекомендуемый пилот

Начать с общей нагрузки отдела. Не пытаться раздать задачи людям по графику
смен или общему Telegram-аккаунту. Показать три вопроса: сколько пришло,
сколько закрыли и растёт ли известный остаток. Затем добавить срок решения
и его распределение, сохраняя различие со временем фактической работы.

Первую партию из 30–50 реальных задач проверить вручную, сопоставляя каждую с
перепиской: не приняты ли обсуждения за задачи, не пропущены ли просьбы,
верно ли выбрано «готово», не задвоена ли карточка из Asana. Накопить перечень
ошибок и уточнить правила. Количество сообщений в JSON не служит числом задач.

Только после этого подключать постоянный Telegram/Asana сбор и автоматический
вызов модели. В текущем архиве ни один коллектор не получает доступ к аккаунтам,
токенам или рабочим чатам автоматически. На VPS ничего не развёрнуто.
