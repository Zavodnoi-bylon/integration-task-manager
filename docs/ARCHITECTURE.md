# Архитектура и правила данных

## Решение

Новый независимый проект использует знакомый интерфейс TheRaw и тот же простой
стек: Vite/JavaScript, FastAPI, psycopg, PostgreSQL. У него собственная БД `activity`,
Compose project `team-activity-explorer`, volume и внутренняя сеть.
Связей с `core.conversions`, курсами валют, AIO API и существующими БД нет.

Для отдела из четырёх человек первая версия намеренно обходится без очереди
сообщений, Redis и нескольких микросервисов. Ввод JSON, анализ и human review
можно запускать вручную. Автоматический сбор затем заменит только входной этап.
Он не должен менять правила идентификации и подтверждения задач.

## Поток информации

Экспорт Telegram / события Asana поступают в хранилище исходных сообщений.
ИИ создаёт предложения задач со ссылками на конкретные версии сообщений.
Человек принимает или отклоняет предложение. Только принятые карточки и события
используются API дашборда. Встроенного обращения к внешней модели сейчас нет.

Один запрос может быть виден в чате клиента, внутреннем чате и Asana.
Это одна задача с несколькими источниками, если есть достаточные доказательства
совпадения. Совпадение слов и близость времени сами по себе не дают надёжной связи.
Уведомление о назначении в Asana не означает, что задача только что поступила.

## Схема БД

Точный DDL: `init/10-schema.sql`. Ниже — назначение таблиц.

| Слой | Таблицы | Содержание и инвариант |
|---|---|---|
| Исходные данные | `raw.sources` | Устойчивый ID источника, отображаемое имя, полнота охвата |
| Исходные данные | `raw.messages` | Одна запись на chat ID + message ID, ссылка на текущую ревизию |
| История | `raw.message_revisions` | Неизменяемое содержание каждой версии, текст, entities, reply, timestamps, raw JSON |
| Предложения | `work.proposals` | Версионированный вывод ИИ/аналитика, состояние proposed/accepted/rejected |
| Подтверждённые данные | `work.tasks` | Устойчивая задача, название, текущая категория, клиент, явный ответственный, revision |
| Жизненный цикл | `work.events` | Запрос, ожидание, готовность, завершение, повторное открытие и отмена |
| Доказательства | `work.evidence` | Связь задачи/события с конкретной ревизией сообщения |
| Эксплуатация | `ops.import_runs` | Хеш файла, версия парсера, состояние импорта, счётчики и безопасный код ошибки |
| Проверка | `ops.review_log` | Кто подписал решение, когда, почему, снимки до и после |
| Охват | `ops.dataset` | Название набора, partial/unknown/complete, пояснение |

Числовые внешние ID хранятся строками. Это избегает потери точности JavaScript
и сохраняет оригинальные идентификаторы. Доказательство привязано к версии,
поэтому последующее редактирование сообщения не меняет основания прежнего решения.

`raw.messages.current_revision_hash` защищён отложенным составным внешним ключом.
`work.evidence` проверяет принадлежность события той же задаче и существование
указанной ревизии. Writer не получает права создавать схемы, удалять таблицы,
менять роли или очищать таблицы через TRUNCATE.

## Импорт и повторная загрузка

- Хеш успешно обработанного файла обеспечивает пропуск точного повтора.
- Ключ сообщения — `telegram-desktop:<chat_id>:<message_id>`; имя чата и имя файла не входят в идентичность.
- Каждая версия получает SHA-256 от канонического JSON записи.
- Старый экспорт добавляет историю, но не откатывает более свежий текст.
- Различное содержимое с одинаковым временем изменения отмечается конфликтом.
- Отсутствие сообщения в неполном экспорте не считается удалением.
- Операции записи защищены PostgreSQL advisory lock и транзакциями.
- Новый импорт предложений не изменяет уже принятую карточку.

Одно предложение описывает полный снимок задачи. При корректировке нужно сохранить
в нём всю подтверждённую историю, а не передать только последнее событие.
Для существующей задачи `--expected-revision` защищает от перезаписи параллельного
решения. Явное `null` может убрать ошибочное имя/клиента; COALESCE здесь не используется.

## События и время

| Событие | Смысл для отчёта |
|---|---|
| `requested` | Подтверждённый исходный запрос; первый такой запрос создаёт показатель «поступило» |
| `observed_open` | Известно, что задача открыта, но исходный запрос/его время не известны |
| `assigned` | Подтверждённое назначение; не считается новым запросом |
| `waiting` | Ожидание; задача остаётся открытой |
| `resumed` | Продолжение работы по открытой задаче |
| `work_ready` | Работа подготовлена; ещё нет подтверждённого завершения |
| `completed` | Подтверждённое завершение |
| `reopened` | Явное повторное открытие той же задачи |
| `cancelled` | Отмена, отдельная от выполнения |

После completed/cancelled только `reopened` открывает задачу снова.
Повторное «готово» без переоткрытия не увеличивает число завершений.
Если сначала видно только завершение, его можно учесть без выдуманного начала:
срок решения остаётся неизвестным. Более позднее обращение по той же карточке
описывается как повторное открытие; оно не подменяет исходное время запроса.
Отрицательные длительности отклоняются.

Каждое событие содержит `time_basis`: `event` (время исходного события),
`message` (время подтверждающего сообщения), `notification` (наблюдаемое время
уведомления), `observed` (другое наблюдение). Время Telegram-уведомления Asana
не выдаётся за точное время действия в Asana. Это основание видно в карточке.

При одинаковом timestamp порядок детерминирован:
requested → observed_open → assigned → reopened → resumed → waiting → work_ready
→ completed → cancelled, затем сравнивается event_id. Это техническое правило
разрешения равных времён, а не восстановление недостающей фактической хронологии.

## Расчёты

Все даты отчёта — Europe/Moscow. URL принимает включительные `from` и `to`;
сервер переводит их в полуоткрытый UTC-интервал до начала следующего дня.
Неделя начинается в понедельник. Первая и последняя неполные недели помечены.

**Поступило** — количество разных задач, первый допустимый `requested` которых
попал в интервал. **Завершено** — количество разных задач с допустимым завершением
в интервале. Отдельно доступны число событий завершения, переоткрытия и отмены.
Для периода unique counts вычисляются заново, не складываются из дней.

**Известно открытых** — число открытых карточек на конец соответствующего дня
или недели. Для этого учитывается история до начала выбранного периода.
Открытая до начала периода задача не исчезает из остатка только потому, что
в течение периода по ней никто не писал. Известный остаток не доказывает полноту
департаментского бэклога: импорт мог не содержать других открытых запросов.

**Медиана срока решения** — медиана календарных часов от первого известного
запроса до последнего допустимого завершения задачи в выбранном интервале.
Каждая задача участвует один раз в интервале. Рядом показываются размер выборки
и число завершённых задач без известного исходного запроса.
Выходные, ночь и ожидание клиента не вычитаются. Это не трудозатраты.

Неизвестное значение — `null`, на экране «—». Отсутствие принятых данных до конца
периода даёт «нет данных». Наблюдаемый ноль возможен, но всегда вместе с охватом.

Категория, клиент и ответственный в текущей версии — актуальные атрибуты карточки,
а не исторический снимок распределения по сотрудникам на выбранную дату.
Исторический статус задачи рассчитывается на конец выбранного периода.
Полная карточка показывает всю известную историю, включая события после него.

## API и доступ

| GET | Результат |
|---|---|
| `/api/health` | Доступность reader connection либо явно включённого demo |
| `/api/meta` | Московская дата, доступные значения, период, охват и свежесть |
| `/api/report` | Итоги, дневной/недельный ряд, категории |
| `/api/tasks` | Отфильтрованный реестр с серверной пагинацией |
| `/api/tasks/{task_id}` | История и доказательства |
| `/api/proposals` | Предложения, ожидающие человеческой проверки |
| `/api/export/tasks` | Полный CSV выбранного среза |

Writer credentials отсутствуют в web-контейнере. API не имеет POST/PATCH/DELETE.
Каждый ответ строится по одному read-only REPEATABLE READ снимку БД.
Между отдельными HTTP-запросами импорт может завершиться; глобальной версии
снимка, фиксирующей сразу весь экран навсегда, первая версия не обещает.

Для четырёх пользователей и небольшого корпуса событий расчёт в Python по
ограниченному снимку проще проверять. Это не обещание неограниченной масштабируемости.
По умолчанию максимум 100 тыс. задач, 500 тыс. событий/доказательств,
10 тыс. ожидающих предложений и 128 MiB снимка. При превышении — явная ошибка,
а не тихое обрезание. Следующий шаг при росте — SQL-агрегации и предрасчитанные
дневные снимки с теми же тестами семантики.

CSV проверяется по количеству строк и размеру до отправки; опасные начала
текстовых ячеек нейтрализуются. Неизвестные API routes дают JSON 404.
Публичный reverse proxy и авторизация — отдельный этап установки.

## Что добавить после пилота

1. Проверить 30–50 настоящих задач вручную: ложные задачи, пропуски, связи «запрос–готово», дубли между чатами и Asana.
2. Утвердить словарь категорий, признаки завершения и правила объединения.
3. Подключить автоматический сбор как новый адаптер raw-слоя, сохранив revision/history.
4. Автоматизировать вызов выбранной модели с версией prompt/model и метриками качества; спорное оставить в review.
5. Добавить авторизованный редактор с отдельным write-сервисом и персональным audit trail, если CLI станет неудобен.
6. После достаточного охвата расширить графики: возраст открытых задач, время первого ответа, распределение сроков и подтверждённые паузы.

График 2/2 и часы смен можно добавить для анализа поступления обращений по сменам,
когда известны конкретные даты дежурств. Сам по себе он не устанавливает исполнителя
и не позволяет достоверно измерить индивидуальную загрузку.
