# Telegram task manager: исследование кандидатов

Дата: 27 октября 2026. Это исследование, не выбор реализации и не развёртывание.

## Последнее уточнение пользователя — приоритет над первоначальным сравнением

Главная цель не менялась: достоверная отчётность и демонстрация работы в существующем UI.
Бот — новый источник структурированных задач, статусов и истории; удобство интерфейса
важно, но не заменяет требования к сохранению данных и связи с отчётом.

- Kalisto и Mephisto — два рабочих Telegram-аккаунта, НЕ два физических сотрудника.
  Клиенты направляются к своему рабочему аккаунту, общей очереди на оба аккаунта не требуется.
  Авторами действий фиксируются доступные Telegram-идентификаторы; физический исполнитель
  не выводится из общего рабочего аккаунта или смены.
- Пользователь допускает два одинаковых бота для разделения потоков. Это предложенный
  вариант, окончательный выбор развёртывания ещё не сделан. Тенанты AIO не определяют роли бота.
- Каждый тикет имеет самостоятельный постоянный ID и явно выбирается обеими сторонами.
  Один пользователь может вести несколько тикетов. Новое сообщение нельзя молча отнести
  к последнему тикету. Технарь работает со всеми клиентскими тикетами своего потока,
  клиент — только со своими.
- Посторонние переписки добавляются вручную: текстом, пересылкой или вложениями.
  Возврата к парсерам сторонних чатов пользователь не запросил.
- Комментарии/заметки доступны технарю. Клиент видит описание и статус; если готовое
  решение поддерживает диалог по тикету, он также видит адресованную ему переписку.
  Внутренняя заметка и публичный ответ — разные действия и типы записи, отправка клиенту
  не должна происходить от обычного добавления внутреннего комментария.
- Вся относящаяся к тикету история должна сохраняться в БД для UI: текст, отправитель,
  время, привязка к тикету, видимость и сведения о вложениях. Хранение бинарных вложений
  и ограничения Telegram file_id требуют отдельной проверки при выборе реализации.
- Создание и каждый переход статуса фиксируются с временем и источником действия;
  повторное открытие не стирает предыдущие закрытия. Повторная доставка update не создаёт дубль.
- Критерий пригодности готового бота: можно достоверно получить ID, описание, текущее
  состояние, историю переходов и сообщения конкретного тикета в существующий UI.
  Не выбирать продукт только за удобную пересылку сообщений или красивое меню.

Ниже сохранено исследование до этих уточнений. Ранние упоминания двух технарей с общей
очередью и изоляции тенантов не являются действующими требованиями. Новый процесс ещё
не реализован, серверные задачи сбора этой работой не отключались.

## Новое направление

### Дополнительный поиск и прагматичный выбор

После запроса пользователя учтён отдельный риск: прежний опыт длительной отладки кнопок.
Готовый репозиторий не снимает этот риск, если приходится заменять его маршрутизацию
сообщений и состояния диалогов. Рекомендация уточнена до гибрида компонентов:
существующая отчётная часть + готовый framework диалогов + собственная ограниченная
логика тикетов. Это по-прежнему разработка нового бота, а не установка готового продукта.
Архитектура ещё не принята; внедрение не начато.

Дополнительно просмотрены через GitHub API:
- [prasx/HelpDesk](https://github.com/prasx/HelpDesk), MIT, push 2025-09-11,
  commit `dc914545712a31229dc2bbae9bd35bebac088eaf`. README и код: aiogram 3/SQLite,
  меню клиента/администратора, заявки с ID, списки и закрытие с комментарием. Но main.py
  использует MemoryStorage; update_ticket_comment заменяет единственное поле ticket_comm,
  update_ticket_status заменяет текущее состояние без добавления события. Отдельной таблицы
  истории сообщений в просмотренной схеме нет. Не считать готовой основой отчётности.

  Нужный выбор карточек клиентом и SQL-совместимость с нашим проектом не подтверждены.

Готовый компонент интерфейса:
[aiogram-dialog](https://github.com/Tishka17/aiogram_dialog), Apache-2.0.
В stable-документации есть Window/Dialog, отдельные контексты, Back/Cancel,
Select и ScrollingGroup. Это уменьшает объём самописной навигации, но не реализует
права, бизнес-статусы, надёжную доставку или устойчивость после рестарта автоматически.
Persistent state, устаревшие кнопки и привязка ticket_id должны проверяться отдельно.
Источник: https://aiogram-dialog.readthedocs.io/en/stable/transitions/index.html

Исправление прежнего пояснения возможностей Telegram: текущая официальная документация
описывает темы в ЛИЧНЫХ чатах с ботом, включаемые через BotFather; createForumTopic
допускает private chat. Это отдельная возможность представить тикеты, не требование
создать группу. Доступность для выбранного бота и поведение клиентов не проверены;
на неё нельзя опираться как на уже испытанное решение. ID темы не заменяет постоянный
ID тикета и журнал в PostgreSQL.
Источники: https://core.telegram.org/bots/features#topics-in-private-chats и
https://core.telegram.org/bots/api#createforumtopic

Прагматичный контроль перед полноценной разработкой: один изолированный вертикальный
прототип, один тестовый бот, два тикета одного клиента. Проверить выбор, Back/Cancel,
внутреннюю заметку без доставки клиенту, публичный ответ, двойное нажатие/старую кнопку,
перезапуск и показ тех же записей в тестовой карточке UI. До прохождения этого сценария
не переносить данные и не разрабатывать остальные меню. Второй бот — конфигурация того
же кода после проверки, а не отдельная ветка/копия реализации.

Важно: текущий backend не готовый ticket API. В activity/task_status.py ручная смена
статуса связана с proposals/raw evidence/ops.tenants. Нельзя просто подключить новые
кнопки к этому обработчику и объявить новый процесс готовым. Нужен согласованный слой
записи тикетов и отображения событий для существующего отчёта с сохранением старой истории.

### Итог повторной оценки по окончательным требованиям

27 октября дополнительно прочитаны обработчики выбора тикета, комментариев и действий
технаря в ранее зафиксированных commits. Это всё ещё статическая проверка: живого пилота
и прогона сторонних тестов не было. Дополнительный адресный поиск не дал подтверждённого
более подходящего готового Telegram-бота.

| Кандидат | Выбор отдельного тикета | Внутренние записи | Данные для нашего отчёта | Решение |
|---|---|---|---|---|
| GLPIgram | Клиентские и технические карточки с ticket_id; очереди в ЛС | API принимает is_private, но проверенная кнопка Comment вызывает публичный add_followup | Через внешнюю GLPI; нужен адаптер к нашему UI/БД | Лучший из готовых по UX, только при отдельном решении внедрять GLPI |
| prettyleaf | Списки есть; при отсутствии активного выбора пользовательское сообщение попадает в найденный открытый тикет | Есть отдельная /note с номером, SQL-таблица заметок | PostgreSQL и сообщения есть; ReopenTicket стирает closed_at, нужен журнал событий | Не брать без разрешения на использование и существенной адаптации маршрутизации/интерфейса |
| bostrot | Операторские /open и /ticket есть; нужный клиентский выбор нескольких задач не подтверждён | Заметки и сообщения предусмотрены | MongoDB, другая интеграция; режимы жизненного цикла требуют проверки | Не выбирать для текущего SQL-проекта |
| xXxMOTxXx | Простой приём/назначение; один активный тикет, обмен контактами | Полноценной таблицы переписки нет | ID и три времени есть, истории комментариев нет | Каркас, не готовое решение |

Конкретные наблюдения:
- prettyleaf `HandleUserMessage`: после отсутствующего/недействительного StateInTicket
  вызывается GetOpenTicketByUserID, затем сообщение пересылается без нового выбора.
  Это статически найденное поведение, не утверждение о воспроизведённом сбое после перезапуска.
- prettyleaf обычный ответ технаря связан с SupportChatID/message_thread_id.
  Отдельные административные команды допускают номер тикета, например `/note`.
  Поэтому неверно говорить, что вообще все действия требуют группы; однако полноценный
  диалог технаря по карточке в личном чате потребует доработки.
- GLPIgram `tech_actions._post_comment` вызывает `client.add_followup(ticket_id, content)`.
  В client.py значение `is_private` по умолчанию False. Возможность API не означает наличие
  нужной кнопки в боте. При добавлении внутренних вложений надо также проверить доставку:
  текущий путь вложений публичного комментария специально отправляет файл заявителю.
- GLPIgram `my_tickets` показывает выбранный ticket_id и отбирает только публичные followups.
  `tech_tickets` предоставляет карточки очереди с кнопками и Back.
- GLPIgram Close создаёт solution/SOLVED и предлагает заявителю подтвердить или вернуть
  работу. Это нужно явно сопоставить с метриками; не считать SOLVED и CLOSED синонимами.

Рекомендация для обсуждения: ни один проверенный репозиторий не выбирать как «поставить
и подключить к UI». Если принципиально нужен готовый backend заявок — пилотировать GLPIgram
с GLPI отдельно, понимая дополнительный стек и адаптер отчёта. Для сохранения существующего
PostgreSQL/API/UI разумная альтернатива — ограниченный Python/aiogram-модуль приёма и ведения
тикетов с двумя конфигурациями ботов. Это предложение архитектуры, не разрешение начать
разработку, не оценка трудозатрат и не обещание, что самописный вариант заведомо дешевле.
В обоих вариантах сначала проверить два одновременных тикета, приватность заметок,
повторы доставки и сохранность истории. Доступ к ботам определяет поток/рабочий аккаунт,
не тенант AIO; идентификаторы двух экземпляров должны быть однозначны для общей отчётности.

Пользователь заменил прежнюю концепцию анализа переписок на создание и ведение
тикетов внутри Telegram-бота. Парсеры, пользовательские Telegram-сессии и серверный
Codex не нужны в целевой цепочке. Их фактическое отключение этой работой не выполнялось.
Существующие данные и развёртывание сохраняются. Использование прежних PostgreSQL
и UI обсуждается; новая схема записи ещё не спроектирована и не применена.

Обязательные требования:

1. Пользователь создаёт отдельный тикет с ID и описанием, получает доступ к его статусу.
2. Технарь получает уведомление и видит открытые задачи внутри Telegram.
3. Технарь меняет статус и пишет комментарий; история доступна в БД и деталях UI.
4. Время создания и переходов фиксируется системой, включая повторное открытие.
5. Уточнение пользователя: тенанты существуют только в AIO и НЕ определяют устройство
   или права нового бота. Ровно два типа пользователей: технари и клиенты.
   Два технаря видят все тикеты всех клиентов; клиент видит только созданные им тикеты.
   Технари используют те же два Telegram-аккаунта, которые ранее авторизованы для collector.
   Технарь принимает тикет, общается с клиентом и меняет статус.
   Тикет — самостоятельная сущность БД; группы/forum topics не являются требованием.
   Требуется проверить работу с карточками и общением через личный диалог с ботом.

Это уточнение заменяет прежнее предположение исследования об изоляции двух тенантов.
Замечания ниже об отсутствии tenant_id сохранены как история первоначальной оценки,
но больше не являются недостатком или критерием выбора. Ранее существующее разделение
данных в отчётной БД этим уточнением не менялось. Число технарей для нового бота — два,
не четыре сотрудника прежнего календаря смен.

Одна переписка на пользователя не равна отдельным задачам. Нужно проверить несколько
одновременных тикетов одного человека и явный выбор тикета для нового комментария.

## 1. prettyleaf/telegram-support-bot

[Репозиторий](https://github.com/prettyleaf/telegram-support-bot),
проверенный commit `68ffe135bc80058b8ea0f569d761e192ce6b251d`.
Go, PostgreSQL, React/TypeScript. Последний push по API: 24 октября 2026.

Подтверждено в коде: отдельные ticket ID/number и forum topic, `/newticket`,
`/mytickets`, `/tickets` с фильтрами и страницами, close/reopen, сообщения и внутренние
заметки в SQL. В README есть веб-панель с деталями, ответами и заметками.
Пример настройки допускает три открытых тикета пользователя; фактическую маршрутизацию
между ними после перезапуска нужно проверить в пилоте.

Таблица tickets содержит created_at/updated_at/closed_at и автора закрытия.
Но ReopenTicket обнуляет closed_at/closed_by: это не полный неизменяемый журнал
переходов. Для наших метрик требуется отдельная история событий.
В просмотренной схеме нет tenant_id. Разделение тенантов и интеграция существующего UI
требуют разработки. Есть специфичные для чужого продукта HWID/Remnawave-сценарии.

В дереве проверенной версии нет LICENSE; GitHub API возвращает license=null.
Разрешение на переиспользование не подтверждено — до выяснения не выбирать как основу.
Наличие тестов в дереве не означает, что мы проверили работоспособность.

## 2. snnrman/glpigram

[Репозиторий](https://github.com/snnrman/glpigram),
commit `28ee462c133ef58a57e6da22a1ac8c39c0187038`, MIT.
Python/aiogram, внешний GLPI 11 через REST; SQLite хранит связи и состояние доставки,
а сами задачи и комментарии — GLPI. Последний push: 14 октября 2026.

README описывает создание с категорией, срочностью, заголовком, телом и вложениями;
«Мои заявки», статусы, комментарии, уведомления. В коде tech_tickets подтверждены
личная очередь исполнителя и очередь неназначенных; tech_actions — действия по ID
тикета и кнопки ответа/закрытия. Есть возврат из карточек в список.
Закрытие включает понятие решения и ожидания подтверждения заявителя: нужно согласовать
его с нашими «завершена» и «закрыта», а не подставлять один статус за другой.

Это наиболее близкий Python-вариант по пользовательскому процессу, но он не автономен:
требуются GLPI, API-учётная запись и привязка пользователей. В README привязка ориентирована
на существующие GLPI/AD-учётки. Перенос текущих tenant-прав и отчётов не подтверждён.
Не считать SQLite этого бота самостоятельной task DB. Развёртывание GLPI — отдельное
архитектурное решение, ещё не принятое пользователем.

[Очереди технарей](https://github.com/snnrman/glpigram/blob/28ee462c133ef58a57e6da22a1ac8c39c0187038/bot/handlers/tech_tickets.py)

## 3. bostrot/telegram-support-bot

[Репозиторий](https://github.com/bostrot/telegram-support-bot),
commit `5c4bb7386da42647bc4e55e3660238a1ab037b19`, GPL-3.0 по GitHub API.
TypeScript/Telegraf, MongoDB. Последний push: 20 октября 2026; 616 stars на момент проверки.

README и исходники описывают ID, открытые/закрытые тикеты, `/open`, `/ticket`,
назначение исполнителя, заметки, сообщения и события аналитики в MongoDB.
Есть категории с направлением в группы и webhooks для интеграции.
Возможности LLM опциональны и для новой концепции не нужны.

Недостатки для нас: другой основной стек хранения, категории не подтверждают изоляцию
тенантов, пользовательский список нескольких задач не подтверждён. В коде есть и режим
ticket_per_message, и старый путь findOneAndReplace по пользователю — сохранение истории
при разных режимах нужно проверять отдельно. SQL-подключение к нашему UI потребует адаптера
или существенной переделки. Популярность не является доказательством корректности.

## Вывод и критерии пилота

Готового решения, проверенно закрывающего все требования и два тенанта в нашем стеке,
не найдено. Shortlist: prettyleaf как близкий самостоятельный продукт с препятствием
по лицензии; GLPIgram как близкий Python-процесс с обязательной внешней платформой.
Bostrot — функциональная альтернатива, но MongoDB расходится с выбранным SQL-хранилищем.

Перед выбором проверить на синтетических данных:
- два одновременных тикета одного пользователя, отсутствие смешения комментариев;
- общая очередь для двух технарей, принятие тикета одним из них и проверка прав на каждое действие;
- создание, закрытие с комментарием, повторное открытие и полную историю времени;
- клиент видит только собственные тикеты, оба технаря — все; проверка чужих ID/callback;
- повтор Telegram update, двойное нажатие, перезапуск между записью и уведомлением;
- получение истории выбранного тикета нашим UI, сохранение её после закрытия;
- Back/Cancel на многошаговых формах и явное различие внутренних/публичных комментариев.

Уточнённый UX: «Новая задача» / «Мои задачи» у заявителя;
«Все задачи» / «Открытые» / «Мои в работе» у технаря. Карточка содержит ID, автора,
исполнителя, описание, статус и историю. Тенант AIO не является ролью/границей доступа.
При нескольких открытых тикетах комментарий должен явно относиться к выбранному ticket_id.
Предпочтение — действия в личном диалоге с ботом; forum group не навязывать.
Предыдущий shortlist не подтверждает полное соответствие этому UX: у prettyleaf
основной рабочий процесс технаря использует forum topics; GLPIgram ближе к личным
карточкам, но также использует группу уведомлений и требует GLPI. Нужна переоценка
готовых решений по уточнённым условиям до выбора основы.
