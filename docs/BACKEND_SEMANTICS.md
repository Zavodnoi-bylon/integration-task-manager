# Правила расчёта и ограничения API

Этот документ описывает реализованные правила `activity/domain.py`. Все примеры
из `examples/demo_dataset.json` синтетические; приложение использует их только
при явном `ACTIVITY_DEMO=1`. Обычный запуск требует PostgreSQL и не подставляет
демонстрационные данные при ошибке подключения. В production image примеры не
включены.

## Даты и история

Параметры `from` и `to` — включительные даты Москвы. Внутри расчёта это интервал
от полуночи `from` до полуночи следующего за `to` дня, с исключённой правой
границей. Максимальная длина — 366 календарных дней. Неделя начинается в
понедельник; обрезанные границами запроса недели имеют `partial: true`.

История до выбранного периода участвует в остатке. Известная открытая задача
остаётся в нём, даже если в выбранном периоде по ней не было сообщений.
`waiting` и `work_ready` — открытые состояния. `work_ready` означает готовность
работы, но не подтверждённое завершение. `assigned` и `observed_open` не создают
входящую заявку.

При одинаковом времени события сортируются в следующем порядке, затем по
строковому `event_id`:

1. `requested` → `observed_open` → `assigned` → `reopened` → `resumed`.
2. `waiting` → `work_ready` → `completed` → `cancelled`.

После закрытия открыть задачу может только `reopened`. Повторное терминальное
уведомление без открытия между ними не создаёт ещё одно завершение или отмену.
`reopened` для уже открытой задачи считается ошибкой последовательности.

Первая видимая запись может быть `completed`: в таком случае наблюдаемое
завершение учитывается, а исходное начало и длительность неизвестны. Более
поздний запрос по той же карточке нельзя выдавать за её первоначальное начало.
Если первоначального `requested` в истории нет, после уже наблюдаемого закрытия
первый `requested` отклоняется. Продолжение отражается через `reopened`/`resumed`
с подтверждением либо через явное исправление исходной истории. Отрицательные
интервалы отклоняются; они не превращаются в ноль.

## Числа и выборки

- Входящие — уникальные задачи с первым допустимым `requested` в периоде.
- Завершённые — уникальные задачи с допустимым `completed` в периоде.
  `completion_events` отдельно показывает число закрытий, включая закрытия
  повторно открытых задач. Периодное число уникальных задач нельзя получать
  сложением дневных или недельных уникальных чисел.
- Известно открытых — состояние на конец каждого интервала, а не сумма дневных
  остатков. При частичном источнике это не весь объём работы отдела.
- Медиана — календарные часы от первого известного запроса до последнего
  допустимого завершения **каждой задачи внутри выбранного интервала**.
  Повторное открытие не сбрасывает исходный запрос; время включает ожидание и
  промежуток между закрытием и повторным открытием. Это не трудозатраты.
  Задачи без исходного запроса исключены из медианы и показаны отдельным счётчиком.
- Нет наблюдаемых принятых задач до конца периода: `empty: true`, числовые
  показатели `null`, график и разбивка пусты. История известна, но в периоде нет
  событий: нулевые наблюдаемые потоки допустимы, предупреждение о покрытии остаётся.

Фильтры категории, клиента и исполнителя применяются к текущим атрибутам
подтверждённой карточки. Прошлое распределение исполнителей не восстанавливается.
`assignee=__unknown__` выбирает карточки с `null`. Автор сообщения и график смен
не используются для определения исполнителя.

`/api/tasks` показывает состояние на конец `to`. Фильтр `status=open` включает
`open`, `waiting`, `work_ready`; `status=waiting` — только ожидание.
`metric=all` выбирает задачи с допустимым событием в периоде либо открытые на его
конец. `metric=completed` выбирает задачи, закрывавшиеся в периоде, даже если
позже они снова открылись; фильтр статуса при необходимости дополнительно
ограничивает результат. `metric=backlog` включает старые задачи без новых событий.
`completed_at` — последнее допустимое завершение до конца `to`, в том числе у
повторно открытой задачи. `resolution_hours` относится к этому завершению.

Карточка `/api/tasks/{task_id}` показывает всю принятую историю и последнее
известное состояние. Идентификатор не преобразуется в число. Ссылки на один и
тот же текст и ревизию в нескольких событиях дают одно подтверждение в карточке;
история событий содержит `counted: false` у повторных терминальных уведомлений.

`/api/proposals` возвращает плоские документы кандидатов с `state`, `created_at`,
`proposal_id`, `task_id`, `version` и `evidence_details`. Последнее поле содержит
текст, автора, время, источник и признаки неполноты для точных ревизий сообщений,
на которые ссылаются кандидат или его события. Повторные ссылки объединяются;
новая редакция сообщения не подменяет процитированную старую. Исходные ссылки
`evidence` сохраняются. Таким образом, подтверждения можно прочитать до принятия
карточки. Кандидаты не участвуют в рабочих показателях.
Число кандидатов в метаданных и отчёте относится ко всей очереди проверки.

## Снимок, ограничения и CSV

Один ответ строится на одном снимке. Репозиторий читает все нужные таблицы в
транзакции `READ ONLY REPEATABLE READ` и использует отдельные reader credentials.
SQL из запроса не принимается. Веб-процесс читает тексты только подтверждений
принятых карточек и кандидатов в очереди проверки; полный `raw_json` и посторонняя
история чатов в ответы не входят.
Отдельного кэша нет. Одновременно разрешены четыре загрузки снимка; соединение
закрывается после загрузки. PostgreSQL statement timeout — 10 секунд.

Лимиты по умолчанию: 100 000 задач, 500 000 событий, 500 000 связей подтверждений,
10 000 кандидатов, 128 MiB сериализованного снимка. Они настраиваются переменными
`ACTIVITY_MAX_TASKS`, `ACTIVITY_MAX_EVENTS`, `ACTIVITY_MAX_EVIDENCE`,
`ACTIVITY_MAX_PROPOSALS`, `ACTIVITY_MAX_SNAPSHOT_BYTES`. При превышении приложение
отвечает 413, не возвращая обрезанный отчёт. Ошибка подключения не раскрывает
строку подключения, SQL или пароль.

Лимит подтверждений также ограничивает совокупность уникальных пар
сообщение/ревизия для принятых задач и кандидатов. Тексты загружаются по точным
парам через параметризованный запрос; объём текстов проверяется до загрузки.
Если один текст встречается у нескольких кандидатов, расширенный ответ очереди
также проверяется по лимиту байтов.

CSV экспортирует всю отфильтрованную выборку, независимо от текущей страницы.
Лимиты по умолчанию — 100 000 строк и 16 MiB; переменные
`ACTIVITY_MAX_EXPORT_ROWS`, `ACTIVITY_MAX_EXPORT_BYTES`. Экспорт полностью
подготавливается до передачи клиенту; при превышении лимита возвращается JSON
ошибки 413, а не частичный CSV. Текст, похожий на формулу, экранируется; числа
остаются числами. `X-Export-Count` содержит полное число строк. Ответы API и CSV
имеют `Cache-Control: no-store`.
